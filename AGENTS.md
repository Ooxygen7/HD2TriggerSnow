# Repository Agent and Pull Request Guidelines

## Scope and precedence

These instructions apply to the entire repository. A more specific `AGENTS.md` in a subdirectory may add or override rules for that directory.

Follow, in order:

1. Explicit maintainer instructions in the current issue or pull request.
2. This file and any more specific repository instructions.
3. Existing project conventions and tests.

AI assistance does not transfer responsibility away from the contributor. The contributor must understand, review, and be able to explain every submitted change.

## Project priorities

This is a Windows Rust/Tauri application with a WebView2 interface and native global input handling. Preserve these priorities:

1. Existing user-visible behavior and backward compatibility.
2. Input safety and predictable shortcut handling.
3. Stability, clear failure handling, and recoverable configuration.
4. Low startup cost, low idle resource usage, and responsive UI behavior.
5. Small, reviewable changes with evidence-based validation.

Do not trade correctness or compatibility for an unmeasured optimization.

## Before making changes

- Start from the latest `main` branch unless a maintainer explicitly requests another base.
- Inspect the current implementation, related tests, open issue, and full PR diff before editing.
- Check the working tree first. Preserve unrelated local changes and never stage them silently.
- Define the intended behavior, backward-compatibility expectations, and validation plan.
- Keep one coherent purpose per PR. Do not bundle unrelated refactors, formatting, network features, or installer changes.
- Prefer the smallest implementation that fully fixes the root cause.

## Branch, commit, and tool naming

- Use descriptive branches such as `feat/...`, `fix/...`, `docs/...`, `refactor/...`, `test/...`, or `chore/...`.
- Do not put the name of an AI model, coding agent, editor, or automation tool in branch names, commit messages, PR titles, release notes, or changelog entries.
- Write commit messages in concise, imperative English and describe the engineering change.
- Keep commits logically scoped. Avoid commits named `update`, `changes`, `AI fix`, or similar vague descriptions.
- Never force-push, delete a branch, bypass branch protection, or push directly to `main` unless a maintainer explicitly authorizes that exact action.

## Implementation rules

### General

- Preserve public behavior unless the issue explicitly requests a behavior change.
- Maintain compatibility with existing `settings.json`, loadouts, presets, custom stratagems, and overlay position data.
- New automatic or potentially disruptive behavior must be opt-in and default to off unless the issue says otherwise.
- Normalize persisted settings defensively. Missing or malformed opt-in values must not silently enable a feature.
- Do not add telemetry, analytics, remote code execution, new update sources, or new network dependencies without explicit approval.
- Validate untrusted input, response size, status codes, timeouts, paths, and data structure before use.
- Never commit credentials, tokens, private URLs, server passwords, personal paths, logs containing secrets, or production configuration.
- Do not include generated installers, `target/`, `node_modules/`, temporary files, local caches, screenshots, or debug logs unless the task explicitly requires a tracked artifact.

### Rust and Tauri

- Keep blocking filesystem, network, OCR, and process work off the Tauri event loop.
- Commands that may create a WebView window must remain asynchronous to avoid Windows event-loop deadlocks.
- Use bounded waits, bounded allocations, and explicit error propagation for native operations.
- Avoid new `unsafe` code. When it is unavoidable, document the invariant and keep the unsafe block minimal.
- Preserve shutdown guarantees: input cancellation, hook cleanup, pending-save flushing, and bounded fallback exit behavior.
- Run formatting and Clippy with warnings denied before submission.

### Native input and shortcuts

- Never allow application-generated `SendInput` events to recursively trigger application shortcuts.
- Filter only input that is positively identified as generated by this application. Do not blanket-reject legitimate input from drivers, remappers, accessibility software, or remote desktop tools.
- Preserve support for single keys, key chords, mouse buttons, wheel bindings, and bindings triggered while unrelated extra keys are held.
- Keep the native input filter synchronized after changes to bindings, loadouts, OCR hotkeys, overlay visibility, or capture state.
- Do not allocate, perform I/O, sleep, or emit noisy logs in low-level hook hot paths.
- Any change to input routing requires regression tests and, when practical, a real interactive Windows input-chain check.

### UI and persisted settings

- Keep Chinese and English labels, descriptions, and status messages in sync.
- Treat text received from files, users, OCR, or servers as untrusted. Use safe text rendering and validated image sources.
- Save the complete intended settings state without erasing independently persisted window position data.
- UI controls must show the actual normalized setting value, including the default state for old configurations.
- A failure in a secondary action must not corrupt visibility state, shortcut routing, or saved configuration.
- User-facing UI changes should include a focused regression assertion and a real Tauri/WebView check when the behavior cannot be proven statically.

### Performance and stability

- Avoid new polling loops, eager window creation, repeated parsing, unnecessary clones, or background work while the application is idle.
- Preserve lazy initialization for expensive windows, OCR models, and network operations.
- Do not claim performance improvements without a reproducible before/after measurement.
- Keep fallback paths bounded and observable. A fallback is not a substitute for fixing a known root cause.

## Required validation

Run the checks relevant to the change from the repository root:

```text
npm run check
npm test
```

Also apply the following when relevant:

- UI changes: run the UI regression suite and verify the affected flow in a real Tauri/WebView2 window.
- Shortcut or input changes: test keyboard, mouse, chords, unrelated held keys, key repeat, cancellation, and synthetic-input recursion on an interactive Windows desktop.
- OCR changes: run OCR matcher tests and verify the capture-to-text path when the environment supports it.
- Window changes: verify main-window and overlay dragging, lock/unlock, hide/show, saved position, scaling, and multi-monitor behavior.
- Installer, release, dependency, or native runtime changes: run `npm run build:bundle` and test both a clean install and an upgrade over the previous release.

If a required check cannot be run, state exactly which check was skipped, why it was skipped, and what risk remains. Never report a check as passed unless it actually ran successfully.

## Pull request requirements

PR titles should be concise English descriptions, preferably using a conventional prefix such as `feat:`, `fix:`, `docs:`, `refactor:`, `test:`, or `chore:`.

Every PR description must include:

- A short summary of what changed.
- The user problem or root cause being addressed.
- The resulting behavior, including defaults and backward compatibility.
- The exact validation commands and results.
- Any manual checks that remain unverified.
- Risks, limitations, migration impact, and rollback notes when applicable.
- A linked issue when one exists.
- Screenshots or a short recording for visible UI changes when practical.

Before requesting review:

- Compare the final branch against the current PR base, not only against an intermediate local merge.
- Confirm the diff contains only intended source and test files.
- Confirm no secrets, build outputs, temporary helpers, debug instrumentation, or unrelated edits are present.
- Resolve merge conflicts deliberately and rerun affected checks afterward.
- Keep the PR in draft state while required work or validation is incomplete.

## Contributor credit and maintainer edits

- Preserve the original contributor's commits and PR authorship when maintainers refine a contribution, when practical.
- Add corrective commits to the existing contributor PR when maintainer edits are enabled and doing so is safe.
- Explain substantial scope changes and thank the contributor for the useful proposal or initial implementation.
- Do not copy a contributor's work into a replacement PR merely to take ownership of the change.
- If a rewrite is necessary, retain clear attribution in the PR discussion and commit history where possible.

## External actions and releases

Do not merge a PR, close an issue, post as a maintainer, create or move a tag, publish or replace a release asset, modify branch protection, or deploy a service unless the maintainer explicitly requested that action.

When release work is authorized:

- Confirm the version and tag format used by the repository.
- Build from the exact reviewed commit.
- Record the artifact name and checksum.
- Keep release notes user-focused and link the relevant issue or PR.
- Verify the downloadable artifact after upload.

## Definition of done

A change is complete only when the final diff is scoped, backward compatibility is addressed, relevant automated checks pass, necessary real-runtime behavior is verified, documentation is accurate, and remaining limitations are stated plainly.
